# Соломон

Личный ИИ-секретарь в Telegram: принимает поручения голосом, текстом и
фотографией, понимает их обычным языком, сохраняет и напоминает в срок —
чтобы человек не держал свои дела в голове.

Документы: `idea.md` (зачем) → `spec.md` (что) → `techspec.md` (как) →
`design.md` (как выглядит). Правила работы — `CLAUDE.md`. Очередь работ —
`specs/README.md`. Визуал большого изменения одобряется прототипом до
кода — `prototype/README.md`.

## Как запустить

Бот живёт на сервере и работает там круглосуточно — как он туда
попадает, в разделе «Бот на сервере» ниже. На этом компьютере
`solomon-bot` не запускается, пока работает серверный: процесс бота с
этим токеном должен быть один (`techspec/16-server.md` §16.3).

Нужны [uv](https://docs.astral.sh/uv/) и Node 24. Перед первым запуском
скопируйте `.env.example` в `.env` и заполните значения — без них процесс
не стартует и скажет, какой переменной не хватает. Кроме токена бота и
ключей Supabase там три значения для разбора поручений: `ANTHROPIC_API_KEY`
(ключ Claude, тратит деньги), `DEEPGRAM_API_KEY` (ключ Deepgram — им
распознаются голосовые и кружки, тоже тратит деньги) и `OWNER_TIMEZONE` —
часовой пояс владельца в виде `Asia/Yekaterinburg`, без него «в пятницу»
не превратить в дату.

```bash
npm --prefix miniapp run dev           # Mini App: адрес печатает Vite
uv run --directory bot solomon-bot     # бот — только для отладки, серверный остановлен
```

Напоминания приходят, пока бот запущен: цикл отправки живёт в том же
процессе, что и опрос Telegram. Бот не работал (перезапуск, сбой
сервера) — созревшее не пропадает, оно лежит в базе и уходит первым
тиком после запуска.

Схема базы — миграции в `supabase/migrations/`: применяются
`supabase db push` из корня репозитория или тем же SQL в редакторе панели
Supabase. Первое подключение проекта — по чек-листу `supabase/README.md`.

Жива ли база — `uv run --directory bot solomon-health`.
Проверки перед коммитом — `node scripts/gate.mjs` (см. `CLAUDE.md`
§«Сдача изменения»); чистые функции Mini App отдельно —
`npm --prefix miniapp test`.

Как помощник понимает поручения — `uv run --directory bot pytest -m live`:
десять русских примеров уходят в Claude по-настоящему и сверяются с
ожидаемым разбором. Нужен ключ, стоит денег, в воротах не участвует.

## Публикация Mini App

Приложение живёт на GitHub Pages репозитория (`techspec/07-deploy.md`):
push в `main` собирает его workflow `.github/workflows/pages.yml` и
выкладывает по адресу `https://<user>.github.io/<repo>/`. Настраивается
один раз:

1. **Репозиторий на GitHub** — публичный: на бесплатном тарифе Pages
   работает только для публичных репозиториев. Секретов в репозитории
   нет (`.env` не коммитится), так что это безопасно.
2. **Settings → Pages → Build and deployment → Source: GitHub Actions.**
3. **Settings → Secrets and variables → Actions → New repository secret**,
   два секрета с теми же значениями, что в `.env`: `VITE_SUPABASE_URL`
   и `VITE_SUPABASE_ANON_KEY`. Оба публичные по замыслу Supabase; ключ
   service-role и токен бота сюда не кладутся никогда.
4. **Push в `main`** (по правилу `CLAUDE.md` §«Сдача изменения»). Вкладка
   Actions → «pages» должна позеленеть; адрес — в шаге deploy. Сборка с
   секретом внутри (`service_role`, токен бота, ключ Claude) падает до
   публикации — так и задумано.
5. **Миграции 005–007** должны быть применены к базе (`supabase db
   push`), иначе кнопка «Сделано», вкладка «О себе» и карточка задачи
   в приложении будут отвечать отказом (007 добавляет колонки источника,
   которые приложение читает).
6. **Кнопка меню в BotFather**: `/mybots` → бот → Bot Settings → Menu
   Button → вставить адрес Pages, назвать «Задачи». После этого кнопка
   слева от поля ввода в чате с ботом открывает приложение.
7. **Проверить вживую**: открыть из Telegram — список задач в теме
   мессенджера; `curl -sI https://<user>.github.io/<repo>/` отвечает 200.

Репозиторий переименован — меняется адрес: workflow подхватит новое имя
сам, а в BotFather адрес правится руками. Репозиторий вида
`<user>.github.io` живёт в корне — тогда `VITE_BASE_PATH` в workflow
ставится в `/`.

## Чтение чатов

Соломон читает выбранные вами личные чаты Telegram — официальным путём
«Автоматизация чатов», без права писать (`techspec/25-chats.md`). Из
переписки он записывает договорённости — кто что обещал — и напоминает,
если вы кому-то не ответили. Группы, каналы и переписка до подключения ему
не видны.

**Подключить** — один раз:

1. В [@BotFather](https://t.me/BotFather): `/mybots` → бот Соломона →
   Bot Settings → Business Mode → Turn on. Без этого бота не выбрать в
   настройках.
2. В Telegram: Настройки → Автоматизация чатов → «Чат-бот» — имя бота
   Соломона.
3. Там же — какие чаты он читает: все личные, кроме исключённых, или только
   выбранные.
4. Права бота — отвечать, помечать прочитанным и прочие — снять все: читать
   они не нужны, а писать в ваши чаты Соломон не должен и не будет.
5. Соломон пришлёт в свой чат вопрос о согласии: что читает, куда
   отправляет, сколько хранит. «Согласен» — начинает читать новые
   сообщения. До ответа сообщения не хранятся и теряются.

**Что дальше.** Разговор затих на 20 минут — Соломон разбирает его и
пишет «Из переписки с Игорем (Telegram) записал: …», под каждым делом —
кнопка «Убрать». Вам задали вопрос, а вы три часа не написали в этот чат —
один раз напомнит. С 22:00 до 08:00 молчит до утра. Переписка хранится 7
дней, дела — обычными задачами в списке. На сервере ничего настраивать не
нужно: бизнес-обновления бот запрашивает у Telegram сам.

**Отключить** — в тех же настройках «Автоматизация чатов»: убрать бота или
чаты. Перестать читать, не отключая, — кнопка «Больше не читать» под
вопросом о согласии.

## Бот на сервере

Бот работает на сервере VoiceFin службой systemd `solomon-bot` от
отдельного пользователя `solomon` (`techspec/16-server.md`). Скрипт
`scripts/deploy-bot.mjs` ходит туда по SSH с этого компьютера по имени
`voicefin-vps` из `~/.ssh/config` — адреса сервера в репозитории нет.
Вход — `root` по ключу: пароль скрипт не спрашивает и зависнуть на нём
не может. Все флаги — `node scripts/deploy-bot.mjs --help`.

**Первая настройка** — один раз:

1. `node scripts/deploy-bot.mjs --setup` — заводит пользователя
   `solomon`, ставит ему uv и Python 3.12, клонирует репозиторий с
   GitHub и ставит зависимости бота. Повторный запуск продолжает с
   несделанного шага и ничего не ломает. Нет на сервере `git` или
   `curl` — скрипт остановится и назовёт их: пакеты системы — хозяйство
   VoiceFin.
2. Остановить бота на этом компьютере — процесс бота один.
3. `node scripts/deploy-bot.mjs --env` — выкладка с ключами: служба
   ставится, автозапуск включается, бот стартует.

**Выкладка нового кода** — после push в `main` с чистыми воротами;
миграции этапа, если есть, — в базу до неё:

```bash
node scripts/deploy-bot.mjs            # pull, зависимости, перезапуск, проверка
node scripts/deploy-bot.mjs --env      # то же и ключи из .env — после их смены
node scripts/deploy-bot.mjs --status   # ничего не меняет: служба, коммит, память, журнал
```

Скрипт откажет до обращения к серверу, если есть незакоммиченные
изменения или `HEAD` не совпадает с `origin/main`: сервер берёт код с
GitHub. После перезапуска он ждёт до 60 с строку `Run polling for bot`
в журнале службы и сверяет коммит на сервере с `HEAD`; не дождался —
показывает хвост журнала. Отката нет: исправление — новым коммитом,
push и выкладкой.

`--env` кладёт на сервер ровно переменные раздела бота из
`.env.example`; значения уходят через stdin `ssh`, в выводе — только
имена. Ключи Mini App, Supabase CLI и секреты функций на сервер не
попадают.

Журнал бота — на сервере:

```bash
ssh voicefin-vps journalctl -u solomon-bot -n 100 --no-pager
ssh voicefin-vps journalctl -u solomon-bot -f      # следить; Ctrl+C — выйти
```

Отладка на этом компьютере — сначала остановить серверного
(`ssh voicefin-vps systemctl stop solomon-bot`), после — поднять его
выкладкой. `TelegramConflictError` в журнале значит, что бот запущен в
двух местах сразу.
