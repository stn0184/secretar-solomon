## Проблема

После 001 у помощника есть вход, а хранить нечего: таблиц нет, правил
доступа нет, и инвариант 5 «принятое поручение не теряется» не на чем
выполнять. Главный сценарий `spec.md` §2.1 не проходит даже в самом
грубом виде: человек пишет — помощник не может ничего записать.
Последнее звено связки «Mini App → Supabase под правилами доступа»
из 001 тоже не проверено вживую — проекта Supabase ещё нет.

## Решение

Заводим две таблицы — входящие сообщения и задачи — с правилами доступа
по владельцу, и проводим по ним самый простой путь без ИИ: бот кладёт
любое текстовое сообщение владельца в базу **буквально** как задачу
и подтверждает «Записал: …», Mini App показывает активные задачи
списком. Понимание поручений (`spec.md` §3.2) — следующий этап: он
заменит буквальную запись разбором, а таблицы и доступ останутся.

Что решено на интервью и вынесено в техспек, чтобы исполнитель
не выводил заново:

- **Схема** — `techspec/03-schema.md`: `messages` и `tasks`, у обеих
  `owner_telegram_id`; колонки из `spec.md` §3.3 (срок, приоритет и
  прочее) не заводятся, пока их некому заполнять.
- **Доступ** — `techspec/04-access.md`: одна политика RLS на таблицу
  для `authenticated` по клейму `telegram_id`, для `anon` политик нет;
  бот ходит service-role ключом и фильтрует по владельцу в `db/`.
- **Слой операций** — `bot/src/solomon/services/`, тот самый «между
  `db` и `handlers`» из `techspec/02-layout.md` §2.2. Обработчик
  зовёт `services.tasks.record_from_message(...)`, тот пишет сообщение
  и задачу через `db/tasks.py` и возвращает результат словами;
  обработчик только отвечает. Таблицу напрямую из `handlers.py`
  не трогать.
- **Поведение бота.** Текстовое сообщение владельца, не являющееся
  командой, → сохраняется сообщение, заводится задача с `title` = текст,
  ответ «Записал: «…»». Не текст (голос, фото, стикер, пересланное без
  текста) → «Пока понимаю только текст» и ничего не сохраняется. База
  не ответила → «Не смог записать: база не ответила. Попробуйте ещё
  раз» и запись в лог — но **не** «Записал» (инвариант 4).
  Обновление, пришедшее повторно, второй задачи не заводит
  (`unique` в §3.2).
- **Mini App.** После полученного токена `lib/tasks.ts` читает
  активные задачи владельца, `App.tsx` показывает их простым списком
  новые сверху. Три состояния по `design.md` §2: загрузка, пусто
  («Задач пока нет. Напишите боту — и она появится здесь»), отказ
  текстом на русском. Стилей сверх существующих `styles.css` не
  добавляется: настоящие экраны — этап 003 с прототипом.
- **Живая проверка** — не в этом этапе, а сразу после: проекта Supabase
  нет, и боевые ключи агенту не даются. Этап оставляет в
  `supabase/README.md` пошаговый чек-лист «Первое подключение проекта»
  (завести проект, применить миграции CLI или SQL-редактором, секреты,
  deploy функции, `.env`, прогон: сообщение боту → «Записал» → список
  в Mini App → запрос с одним anon-ключом получает отказ). Человек
  проходит его сам и закрывает строку «Статус проверки связки»
  в `techspec/00-adr.md`.

## Чего не делаем

- Не подключаем Claude API и не разбираем смысл: задача = текст как есть.
- Не заводим напоминания, память о пользователе и журнал — свои этапы,
  таблицы появятся с кодом, который их заполняет.
- Не отмечаем выполнение ни словом, ни кнопкой, ни в Mini App: как это
  делается — открытая развилка `spec.md` §5, решается прототипом 003.
  Колонка `status` есть, но менять её нечем.
- Не сохраняем голос и фото — только вежливый отказ. Приём голоса —
  вместе с распознаванием речи (`spec.md` §5).
- Не даём боту команду «показать список»: список — это Mini App.
- Не рисуем экран: список без дизайна, `design.md` не трогается.
- Не поднимаем локальный стек Supabase (Docker, Deno) и не тестируем
  SQL политик автоматически: RLS проверяется вживую по чек-листу.
- Не пишем в базу из Mini App: только чтение. Правка и создание из
  приложения — этап экранов.

## Приёмка

Проверяется тестами и сборкой, если не сказано «вживую»; «вживую» —
человек по чек-листу `supabase/README.md` после заведения проекта.

- КОГДА владелец присылает боту текст, не являющийся командой, и база
  отвечает, бот ДОЛЖЕН ответить «Записал: «<текст>»», а в базе
  ДОЛЖНЫ появиться одна строка `messages` и одна `tasks` с этим текстом
  и `owner_telegram_id` владельца.
- КОГДА база не отвечает или отвечает ошибкой, бот ДОЛЖЕН ответить, что
  записать не смог, и НЕ ДОЛЖЕН говорить «Записал».
- КОГДА владелец присылает голос, фото или стикер, бот ДОЛЖЕН ответить,
  что пока понимает только текст, и НЕ ДОЛЖЕН ничего сохранять.
- КОГДА одно и то же обновление приходит дважды, в базе ДОЛЖНА остаться
  одна задача.
- КОГДА `db/` вызывается без `owner_telegram_id`, вызов ДОЛЖЕН быть
  невозможен по сигнатуре (аргумент обязателен, без значения по
  умолчанию).
- КОГДА Mini App получила токен и у владельца есть активные задачи,
  она ДОЛЖНА показать их списком, новые сверху.
- КОГДА активных задач нет, Mini App ДОЛЖНА показать объяснение и что
  делать, а не пустой список.
- КОГДА запрос к базе из Mini App не прошёл, Mini App ДОЛЖНА показать
  причину текстом на русском, а не пустой экран.
- КОГДА миграции применены к пустому проекту, обе таблицы ДОЛЖНЫ иметь
  включённый RLS (миграция содержит `enable row level security` для
  каждой).
- Вживую: КОГДА запрос к `tasks` идёт с одним anon-ключом, база ДОЛЖНА
  вернуть пустой результат или отказ; КОГДА тот же запрос идёт с
  токеном `telegram-auth`, база ДОЛЖНА вернуть задачи владельца.
