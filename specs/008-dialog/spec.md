## Проблема

Когда в поручении не хватает главного — «срочно отправить расчёт»
без срока, «я обещал перезвонить» без кого, — бот записывает как есть
и просит «допишите, если важен». Человек дописывает следующим
сообщением — а бот заводит из него **вторую** задачу «в пятницу», не
связывая с первой. Шаг 3 главного сценария `spec.md` §2.1 («задаёт один
вопрос») не работает: напоминать по такой задаче нечем, срока нет.

## Решение

Модель получает право задать **один** короткий вопрос, когда без ответа
поручение не выполнить (`techspec/10-dialog.md` §10.1). Задача
записывается сразу, вопрос — второй фразой ответа и в базе у задачи.
Следующее сообщение владельца (текст или голос) уходит модели вместе с
вопросом; модель решает, ответ это или новое поручение (§10.2). Ответ
дополняет ту же задачу одной транзакцией: поля, перепланированные
напоминания, вопрос закрыт — бот отвечает «Понял: … Срок: … Напомню:
…». Новое поручение — вопрос снимается, задача остаётся с пометкой.
Вопрос живёт сутки (§10.3).

Что решено на интервью и вынесено в техспек:

- **Записать сразу, ответ дополнит** — §10.1: задача с `needs_review`
  и `open_question` появляется до ответа; не ответили — ничего не
  потеряно.
- **Модель решает, ответ ли это** — §10.2 и §5.2 блок 4: в промпт
  уходит открытый вопрос с сутью и полями задачи; ответ —
  `answers_question = true` и только изменённые поля.
- **Срок жизни** — §10.3: до следующего сообщения или сутки, без
  переспрашивания.
- **Один вопрос на владельца** — §10.1: новый снимает старый.
- **Чем снимается вопрос** — §3.4, §10.3: любой записанный разбор
  очищает открытые вопросы владельца (ответ, новое поручение,
  разговор, сведение о себе, вопрос старше суток — одним правилом);
  новый вопрос ставится уже после. Повтор обновления вопросов не
  трогает.
- **Схема** — §3.3: `open_question`, `question_asked_at`;
  `record_understanding` — `amend` (§3.4): обновить поля, снять
  неотправленные напоминания, спланировать новые, закрыть вопрос.
- **Тексты** — «Записал: <суть>. <Вопрос>» при вопросе (без строки
  «Напомню», если срока нет); «Понял: <суть>. Срок: … Напомню: …» при
  ответе; при `answers_question`, но модель снова не уверена —
  «Понял: … <review_reason>».
- **Чтение открытого вопроса** — как известные факты (§8.2): до
  модели, с явным владельцем; сбой чтения — в лог, разбор без блока.
- **Живой прогон** — в `understanding.jsonl` три примера: поручение,
  требующее вопроса (`question` не пуст); ответ на вопрос
  (`answers_question`, `due_at`); новое поручение при открытом
  вопросе (`answers_question = false`).

## Чего не делаем

- Не задаём второй вопрос по той же задаче и не переспрашиваем по
  таймауту.
- Не считаем свайп «ответить» в Telegram признаком ответа: решает
  модель по содержанию.
- Не спрашиваем по идеям, желаниям, разговору и сведениям о себе.
- Не показываем открытый вопрос в Mini App — карточка не меняется.
- Не даём править задачу словами без вопроса («нет, в четверг» после
  «Записал» без вопроса) — это этап правки задачи.
- Не держим больше одного открытого вопроса и не ведём очередь.
- Не меняем поведение при отказе модели и распознавания.

## Приёмка

Проверяется тестами без сети, если не сказано «вживую»; «вживую» —
владелец после миграции и перезапуска бота.

- КОГДА модель вернула задачу с `question`, в `tasks` ДОЛЖНА появиться
  строка с `needs_review = true`, `open_question` = вопрос,
  `question_asked_at`, а ответ бота ДОЛЖЕН быть «Записал: <суть>.
  <вопрос>» без строки «Напомню» при отсутствии срока.
- КОГДА у владельца уже была задача с открытым вопросом и модель
  вернула новый `question`, прежняя задача ДОЛЖНА потерять
  `open_question`, оставшись с `needs_review`.
- КОГДА есть открытый вопрос не старше суток, промпт следующего
  сообщения ДОЛЖЕН содержать блок «Открытый вопрос: …» с сутью и
  полями задачи.
- КОГДА модель вернула `answers_question = true` с `due_at`, задача
  ДОЛЖНА получить новые поля, потерять `open_question`, её
  неотправленные напоминания — замениться на спланированные по новому
  сроку, новая задача — НЕ появиться, а бот — ответить «Понял: <суть>.
  Срок: … Напомню: …».
- КОГДА модель вернула `answers_question = true`, но снова поставила
  `needs_review`, задача ДОЛЖНА получить новые поля и потерять
  `open_question`, оставшись с `needs_review`, а бот — ответить
  «Понял: <суть>. <review_reason>» без второго вопроса.
- КОГДА модель вернула `answers_question = false`, ДОЛЖНО произойти
  обычное: новая задача (или разговор), а открытый вопрос — сняться.
- КОГДА при открытом вопросе пришёл разговор или сведение о себе
  (`task = null`), открытый вопрос ДОЛЖЕН сняться.
- КОГДА для сообщения задача уже заведена (повторный разбор после
  сбоя), `record_understanding` ДОЛЖНА вернуть её, не трогая открытые
  вопросы — вопрос, поставленный первым проходом, остаётся.
- КОГДА вопрос старше 24 часов, промпт НЕ ДОЛЖЕН содержать блок, а
  `open_question` ДОЛЖЕН очиститься при записи следующего разбора.
- КОГДА чтение открытого вопроса упало, разбор ДОЛЖЕН пройти без
  блока, ошибка — в лог.
- КОГДА ответ пришёл голосовым, ДОЛЖНО произойти то же, что с текстом.
- КОГДА `amend` пришёл с чужим или несуществующим `task_id`, база
  ДОЛЖНА отказать, ничего не записав.
- КОГДА задача, идея или желание не требуют уточнения, `question`
  ДОЛЖЕН быть `null`, а поведение — как до этапа (без второй фразы).
- Вживую: КОГДА владелец пишет «срочно отправить расчёт клиенту», бот
  ДОЛЖЕН спросить срок; КОГДА следом «в пятницу» — ответить «Понял: …
  Срок: пятница, …»; КОГДА следом «купить лампочку» — завести новую
  задачу, не трогая первую.
