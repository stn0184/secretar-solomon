## База

### Ядро правки — `change_task`

`change_task(owner_telegram_id bigint, task_id uuid, changes jsonb,
schedule jsonb default null) returns tasks`, `security invoker`. Тело —
бывшее тело `edit_task`: те же правила ключей и те же отказы (префикс
текста сменился на `change_task:`, регэкспы прежних тестов на префикс не
смотрят).

- `schedule = null` — путь приложения: расписание считает сама база
  (`reminder_plan` по поясу из `owner_settings`), перенос ставит
  `due_moved_at`.
- `schedule` — массив `[{stage, fire_at}]` — путь чата: при смене срока,
  точности или вида неотправленные удаляются и вставляется ровно этот
  план (`on conflict on constraint reminders_task_id_stage_key do update
  … sent_at = null`); `due_moved_at` не трогается. Пустой массив —
  стучать не о чем (снятие срока, срок в прошлом).
- **Под токеном ядро равно `edit_task`.** Если `current_user =
  'authenticated'`, владелец из аргумента должен совпасть с клеймом
  `telegram_id` (иначе `null`, ничего не записано), а `schedule`
  отбрасывается: расписание считает база и ставит отметку. Сверх того
  работает RLS (функция invoker). У `anon` права нет.
- Права: `authenticated` (его зовёт `edit_task`, она invoker) и
  `service_role` (его зовёт правка из чата).

`edit_task(task_id, changes)` — обёртка: `return change_task(<клейм>,
task_id, changes, null)`; сигнатура, права и поведение прежние.

### Правка из чата — `edit_from_chat` и форма `edit`

Форма jsonb-аргумента `edit` у `record_understanding` и `pick_task`:

```
{
  "task_id":  uuid,                        -- задача из списка
  "action":   "change" | "done" | "cancel",
  "changes":  {title?, due_at? | due_date?, priority?, promise?, people?},
  "schedule": [{stage, fire_at}],          -- готовый план (§12.4)
  "question": text | null                  -- question верхнего уровня
}
```

`changes` — ключи ядра (`due_at` со смещением — точность `time`,
`due_date` — `day`, `due_at: null` — снять срок). `kind` бот не шлёт:
вид словом не меняется. Нет `schedule` — считается пустым: путь чата
отметку «перенёс» не ставит никогда.

Разбирает её `edit_from_chat(owner_telegram_id bigint, edit jsonb)
returns tasks` (только `service_role`) — одна на `record_understanding`
и `pick_task`:

- `done` / `cancel` — `status = done` / `cancelled`, неотправленные
  напоминания удалены (как `mark_task_done`);
- `change` с непустым `question` — только `needs_review = true`,
  `open_question`, `question_asked_at = now()`; поля не трогаются;
- `change` с пустыми `changes` — ничего не меняется («менять нечего»),
  задача только проверяется на активность;
- `change` с `changes` — `change_task(owner, task, changes, schedule)`.

Задача не активна (`done`, `cancelled`), чужая или её нет — `null`,
ничего не записано. Незнакомое действие — исключение.

### `record_understanding`

Новый последний аргумент `edit jsonb default null`, 13-аргументная
версия удаляется (`drop function`), права — только `service_role`.
Порядок:

1. Сообщение обновляется разбором и ответом, как раньше; прежний
   `messages.task_id` читается тем же `update … returning`.
2. Память — как раньше.
3. Повтор: у сообщения уже есть `task_id` (или задача с
   `source_message_id`) — вернуть её, ничего не править.
4. Вопросы владельца снимаются, если есть разбор, задача, `amend` или
   `edit`.
5. `amend` — как раньше, но отказ по «не активна» (решение 1) и
   `on constraint`.
6. `edit` — `edit_from_chat`; `null` — исключение `record_understanding:
   task % is not an active task of %`, транзакция откатывается целиком.
7. Новая задача — как раньше.

`messages.task_id` пишется в ветках 5, 6, 7 — задачей, которую вернула
ветка.

### `pick_task`, `reopen_task`, закрытие

- `pick_task(owner_telegram_id bigint, message_id uuid, edit jsonb,
  reply text) returns messages` — только `service_role`. Сообщение
  владельца берётся `for update`; не его — исключение. `task_id` уже
  есть (второе нажатие, другая кнопка) — строка как есть. Иначе
  `edit_from_chat`: `null` — строка как есть (`task_id` пуст — бот
  отвечает «Задачу уже закрыли или удалили…»); задача — записать
  `task_id` и `reply`, вернуть строку. Бот отличает свою запись от
  прежней по `task_id` и `reply` в ответе: совпали с его — его ответ и
  кнопка «Вернуть» (для закрытия и уборки), нет — сохранённый текст без
  кнопок.
- `reopen_task(owner_telegram_id bigint, task_id uuid, schedule jsonb)
  returns tasks` — только `service_role`. Нет задачи — `null`; активная —
  как есть, без записи; иначе `status = active`, неотправленные
  удалены, план вставлен с `on conflict … sent_at = null` (взведение
  ушедших ступеней). План считает бот у `reminder_plan` на момент
  нажатия — строка «Напомню» называет записанное.
- `mark_task_done` и `complete_task` — `create or replace`: неактивная
  задача (`done` или `cancelled`) возвращается как есть **до** удаления
  напоминаний — ничего не тронуто.

### Схема

- `tasks_status_check` пересоздаётся: `active`, `done`, `cancelled`.
- `messages.task_id uuid references tasks on delete set null`, у старых
  строк — из `tasks.source_message_id`. Индекс `(owner_telegram_id,
  received_at) where task_id is not null` — под «последнюю задачу».
  Удаление задачи из приложения под RLS обнуляет ссылку: ссылочные
  действия правилам доступа не подчиняются.

## Бот

- `services/edits.py` — чистые функции: порядок и нумерация списка
  (`number_tasks`), номер → задача, строки блока 5
  (`format_open_tasks`), строка свайпа (`swipe_line`), выбор последней
  задачи по событиям, правка для базы из разбора (`edit_changes`: только
  то, что отличается от задачи; день — `due_date` в поясе владельца, час
  — `due_at` со смещением).
- `analyze(…, tasks=None, last_task=None, swipe=None)`: `tasks = None` —
  блока 5 нет (пересланное, сбой чтения), `[]` — «Открытых задач нет.» и
  правила.
- Строка свайпа — в сообщении `user` после «Переслано от» и «Распознано
  с голоса», прямо перед текстом.
- Свайп. Ответ боту: задача по `reminders.telegram_message_id` —
  «Ответ на напоминание о задаче №N»; напоминание о задаче вне списка —
  «Ответ на напоминание: «…»» (строка без номера, с текстом); другое
  сообщение бота — «Ответ на сообщение бота: «…»». Ответ себе:
  `messages.task_id` по `telegram_message_id` — «Ответ на своё сообщение
  о задаче №N», иначе «Ответ на своё сообщение: «…»» (текст из Telegram,
  у голосового — расшифровка из базы). Текст — до 200 знаков. Текста
  нет — строки нет. У пересланного свайп не читается.
- Последняя задача: два события за час — последнее сообщение владельца
  с `task_id` и последнее ушедшее напоминание; берётся более позднее. Его
  задачи нет в списке (закрыта) — строки нет, к более раннему событию не
  откатываемся.
- Чтение контекста и запись по кнопкам — протокол `EditStore` в
  `services/tasks.py` с реализацией поверх `db/`. `TaskService` без
  хранилища видит пустой список (блок «Открытых задач нет.»): прежние
  тесты сервиса не меняются.
- `RecordOutcome.buttons: tuple[Button, ...]`, `Button(text, data)`.
  Повтор обновления — `_repeated`, без кнопок.

## Решения по неоднозначностям

1. **Отказ `amend` — «не активна», а не `status = 'done'`.** Код
   миграции 008 уже фильтрует `status = 'active'`; правится текст §3.4,
   в `record_understanding.test.ts` добавлен отказ по `cancelled`.
2. **Форма `edit`** — выше, «Правка из чата»; дописывается в §3.4.
3. **`question` в правке — верхнего уровня.** Он действует только в
   ветке «задача узнана, `change`». В ветке «не найдено, перенос» новая
   задача пишется без `open_question`: вопрос был о правке, а не о новом
   поручении (тест сервиса). В ветке кандидатов вопрос ждёт выбора и
   ставится на выбранную задачу.
4. **«Вернул в работу» при сроке в прошлом — без «Напомню»**, как
   перенос (§12.5): план пуст — строки нет.
5. **Перенос вместе с другими полями.** «Перенёс: …» называет и смену
   срочности (§12.5), и новых людей («Люди: …») — как «Поправил».
   Срочность, вернувшаяся к `normal`, звучит «Приоритет: обычный».
6. **«Менять нечего» пишет `edit`** с пустыми `changes`: задача
   проверяется на активность и становится `messages.task_id` — сообщение
   о ней (последняя задача в разговоре), но ничего не меняется.
7. **Не найдено, перенос:** поля новой задачи — верхнего уровня; нет там
   срока — срок из `edit`. Вид верхнего уровня не задача, идея или
   желание — «Не нашёл… ничего не менял».
8. **Номер вне списка** и кандидаты, из которых ни одного нет в списке,
   — не найдено. Кандидатов больше пяти — первые пять.
9. **Кнопка кандидата**: суть до 40 знаков и короткий срок («2 окт»,
   «2 окт, 17:00»). Вопрос о переносе называет новый срок в винительном
   падеже («на пятницу, 2 октября», «на сегодня в 17:00»).
10. **Сбой при нажатии** кнопки кандидата — «Не смог записать правку:
    база не ответила. Попробуйте ещё раз.» всплывающим ответом,
    сообщение с кнопками остаётся (как «Сделано», §6.3). Сообщения
    владельца нет в базе — «Не нашёл эту задачу.»
11. **Отказ модели** — путь «как есть» (§5.4), правка не угадывается.
