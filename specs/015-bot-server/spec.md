## Проблема

Бот работает на компьютере владельца — и только пока его запустили
руками. Компьютер выключен или бот не запущен — напоминания не
приходят, а сообщения ждут, пока бота не поднимут. Разведка 2026-10-01:
когда бот работал, опоздавших напоминаний не было (12 из 12 ушли за
0–1 мин) — дыра не в цикле напоминаний, а в том, что бот не живёт
постоянно.

## Решение

Бот переезжает на сервер VoiceFin — VPS автора, который уже оплачен:
служба systemd от отдельного пользователя, Python через uv, код —
клоном репозитория с GitHub. Новый код попадает туда после push в
`main` одной командой с компьютера владельца — `node
scripts/deploy-bot.mjs`: она забирает код на сервер, ставит
зависимости, перезапускает бота и проверяет, что он поднялся. Как
устроено — `techspec/16-server.md`.

Решения владельца (2026-10-01): бот — на сервер, сервер — VoiceFin.
Сервер осмотрен только на чтение: Telegram, Deepgram, Supabase и
посредник Claude с него открываются, памяти и места хватает (§16.1).

Код бота не меняется. Этап заводит файлы выкладки и правит документы.
Сам переезд — первая настройка сервера, ключи, остановка бота на
компьютере и запуск на сервере — делает оркестратор после закрытия
этапа, с отдельного разрешения владельца на запись на сервер VoiceFin;
тогда же проверяются пункты «при выкладке» из «Приёмки». Их провал —
исправление следующим коммитом, этап не переоткрывается.

## Чего не делаем

- Не трогаем VoiceFin: его контейнеры, Caddy, папки, брандмауэр,
  подкачку, журнал, обновления и перезагрузку сервера (§16.6).
- Не ходим на сервер из этапа: исполнитель не запускает `ssh` и
  скрипт выкладки против сервера — всё проверяется тестами без сети.
- Не открываем портов и не заводим API на сервере: Mini App
  по-прежнему ходит в Supabase напрямую.
- Не собираем образ Docker и не выкладываем из GitHub Actions: ключа
  от сервера VoiceFin в секретах GitHub не будет.
- Не заводим мониторинг и оповещения о падении бота.
- Не защищаемся от второго экземпляра кодом и не откатываем выкладку
  автоматически (§16.3, §16.4).
- Не кладём в репозиторий адрес и порт сервера, ключи и содержимое
  `.env`.
- Не меняем код и тексты бота, кроме докстринга `db/client.py`: /help
  говорит «напоминания приходят, пока я запущен» — на сервере это
  по-прежнему правда.
- Не фильтруем workflow Pages по путям.

## Приёмка

До выкладки — тестами без сети:

- КОГДА скрипт выкладки собирает ключи для сервера, список ДОЛЖЕН
  читаться из раздела бота в `.env.example` и быть ровно
  `TELEGRAM_BOT_TOKEN`, `OWNER_TELEGRAM_ID`, `OWNER_TIMEZONE`,
  `SUPABASE_URL`, `SUPABASE_SERVICE_ROLE_KEY`, `ANTHROPIC_API_KEY`,
  `ANTHROPIC_BASE_URL`, `DEEPGRAM_API_KEY`.
- КОГДА в `.env` владельца есть `VITE_*`, `SUPABASE_ACCESS_TOKEN`,
  `SUPABASE_DB_PASSWORD` и другие переменные вне списка, `.env` для
  сервера НЕ ДОЛЖЕН их содержать; КОГДА переменной из списка в `.env`
  нет, её НЕ ДОЛЖНО быть и в `.env` для сервера, а скрипт НЕ ДОЛЖЕН
  отказывать.
- КОГДА скрипт кладёт ключи, значения ДОЛЖНЫ уходить на сервер только
  через stdin `ssh` и НЕ ДОЛЖНЫ попадать ни в аргументы команды, ни в
  вывод скрипта — там только имена.
- КОГДА `.env` владельца или файлы `deploy/` записаны с переводами
  строк Windows, на сервер ДОЛЖНЫ уйти строки с LF.
- КОГДА рабочее дерево не чистое или `HEAD` не совпадает с
  `origin/main`, скрипт ДОЛЖЕН отказать до первого обращения к серверу
  и сказать, что сделать.
- КОГДА скрипт выкладывает, команды внутри папки бота (`git`, `uv`,
  запись `.env`) ДОЛЖНЫ выполняться от имени `solomon`, а файл службы —
  ставиться из копии владельца, не из клона на сервере.
- КОГДА служба после перезапуска не `active` или в её журнале за 60 с
  нет строки начала опроса Telegram (`Run polling for bot`), скрипт
  ДОЛЖЕН завершиться с ошибкой и показать последние строки журнала;
  КОГДА строка есть и коммит на сервере равен `HEAD` — сказать об
  успехе и назвать коммит.
- КОГДА скрипт запущен с `--status`, он НЕ ДОЛЖЕН ничего менять на
  сервере: ни `pull`, ни `sync`, ни записи файлов, ни перезапуска.
- КОГДА читают `deploy/solomon-bot.service`, в нём ДОЛЖНЫ быть
  `User=solomon`, `ExecStart` на `bot/.venv/bin/solomon-bot`,
  `Restart=always`, `RestartSec=10`, `MemoryMax=300M`,
  `CPUQuota=100%`, `WantedBy=multi-user.target`, `NoNewPrivileges`,
  `PrivateTmp`, `ProtectSystem=full`.

При выкладке — оркестратор на сервере, после закрытия этапа:

- КОГДА первая настройка и выкладка с ключами сделаны, служба
  `solomon-bot` ДОЛЖНА быть `active` и `enabled`, процесс бота — от
  пользователя `solomon`, а `--status` — показывать коммит, равный
  `HEAD`.
- КОГДА `setup-server.sh` запускают второй раз, он ДОЛЖЕН закончиться
  успешно, ничего не переделав.
- КОГДА смотрят `.env` на сервере, у него ДОЛЖНЫ быть права 600 и
  владелец `solomon`, а имена переменных — только из списка (сверка по
  именам, без значений).
- КОГДА процесс бота убит, systemd ДОЛЖЕН поднять его не позже чем
  через 30 с.
- КОГДА бот на компьютере остановлен, а на сервере запущен, владелец
  ДОЛЖЕН получить ответ на голосовое поручение с напоминанием через
  несколько минут, а затем и само напоминание.
- КОГДА бот работает на сервере первые 10 минут, в журнале службы НЕ
  ДОЛЖНО быть `TelegramConflictError`.
- КОГДА переезд закончен, контейнеры VoiceFin ДОЛЖНЫ работать с тем же
  временем старта, что до него.
