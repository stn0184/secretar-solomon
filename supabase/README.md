# supabase — база и Edge Functions

Данные живут в Supabase (Postgres, бесплатный тариф). Своего постоянно
доступного сервера у проекта нет, поэтому Mini App ходит в базу **напрямую**,
а ограничивает её сам Postgres — правила доступа (RLS).

## Что здесь лежит

| Путь | Что это |
| --- | --- |
| `migrations/` | Схема и правила доступа: по файлу на изменение, применяются по порядку имён |
| `functions/telegram-auth/` | Edge Function: проверяет подпись Telegram и выдаёт токен |
| `functions/_shared/` | Общий код функций: проверка initData, подпись JWT, uuid владельца |
| `types/deno.d.ts` | Описание того куска Deno, которым пользуются функции — чтобы `tsc` проверял типы без установленного Deno |
| `config.toml` | Настройки проекта для Supabase CLI |

В базе четыре таблицы: `messages` — входящие сообщения как есть вместе с
разбором модели (`analysis`, модель и токены), `tasks` — задачи с разобранными
полями: вид, срок, приоритет, обещание, люди, открытый уточняющий вопрос,
`reminders` — когда о задаче
напомнить и ушло ли напоминание, `facts` — память о человеке: одна
запись — одно обстоятельство одной фразой, факт или предположение.
Все четыре несут `owner_telegram_id`, на всех включены правила доступа.
Что в них лежит и почему — `techspec/03-schema.md`, кто и каким ключом ходит —
`techspec/04-access.md`. Применённая миграция не правится: следующая правка —
следующий файл.

## Как проверяется, что человек — это он

1. Telegram открывает Mini App и передаёт ей `initData`, подписанные ключом,
   выведенным из токена бота.
2. Mini App отправляет `initData` в `telegram-auth`.
3. Функция пересчитывает подпись (токен бота знает только она), проверяет
   свежесть `auth_date` и что это владелец, и подписывает JWT секретом проекта.
4. Mini App отдаёт этот JWT в каждый запрос к базе — PostgREST принимает его,
   выдаёт роль `authenticated`, и дальше запрос ограничивают правила доступа.

Без токена запрос идёт с анонимным ключом и роли `authenticated` не получает.

Клеймы токена: `sub` — постоянный uuid владельца (UUIDv5 от Telegram-id),
`telegram_id` — сам id, `role` и `aud` — `authenticated`, срок жизни час.
Правила доступа смотрят на `telegram_id`, а не на `sub`: тот же id знает бот,
и одна колонка служит обеим сторонам без пересчёта uuid
(`techspec/04-access.md` §4.4).

## Первое подключение проекта

Пройден 2026-09-18, связка закрыта (`techspec/00-adr.md`). Список
остаётся на случай нового проекта. Что выяснилось по дороге: секреты
функций не могут начинаться с `SUPABASE_`; на странице JWT Keys ключ
«Legacy HS256» должен оставаться хотя бы в «previously used» — по нему
база проверяет токены функции; загружать функцию без Docker —
`supabase functions deploy telegram-auth --use-api`.

1. **Завести проект** на supabase.com (бесплатный тариф, регион поближе)
   и привязать репозиторий к нему:

   ```bash
   supabase login
   supabase link --project-ref <ref>
   ```

2. **Применить миграции** — из корня репозитория:

   ```bash
   supabase db push
   ```

   Без CLI — открыть SQL-редактор в панели проекта и выполнить файлы из
   `migrations/` по порядку имён, целиком и по одному.

3. **Проверить, что правила доступа включены.** В панели: Database → Tables →
   `messages`, `tasks`, `reminders` и `facts`, у всех должен стоять RLS, у
   каждой одна политика `owner only` для роли `authenticated`. Таблица без RLS — находка уровня
   безопасности (инвариант 2), а не недоделка.

4. **Положить секреты функции** (значения — из @BotFather и из Settings → API):

   ```bash
   supabase secrets set TELEGRAM_BOT_TOKEN=... OWNER_TELEGRAM_ID=... \
     JWT_SIGNING_SECRET=...
   supabase functions deploy telegram-auth
   ```

   `JWT_SIGNING_SECRET` — «JWT secret» из настроек проекта (Settings → JWT Keys → Legacy JWT Secret; имя без префикса SUPABASE_ — такие имена Supabase в секретах не принимает).
   Если проект уже переведён на асимметричные ключи подписи и общего секрета
   нет, функция переписывается на выдачу сессии через Supabase Auth — см.
   `techspec/00-adr.md`, строка про проверку человека.

5. **Заполнить `.env`** в корне репозитория по `.env.example`: адрес проекта,
   ключ service-role для бота, адрес и анонимный ключ для Mini App, ключ
   Claude (`ANTHROPIC_API_KEY`), ключ Deepgram (`DEEPGRAM_API_KEY`) и часовой
   пояс владельца (`OWNER_TIMEZONE`, например `Asia/Yekaterinburg`) — без
   них бот не стартует. Проверить
   связь — `uv run --directory bot solomon-health`.

6. **Прогнать путь целиком.** Запустить бота (`uv run --directory bot
   solomon-bot`) и Mini App (`npm --prefix miniapp run dev`, открыть из
   Telegram):

   - написать боту «в пятницу отправить расчёт клиенту» — он отвечает
     «Записал: отправить расчёт клиенту. Срок: пятница, …»;
   - в таблицах `messages` и `tasks` появилось по строке с вашим
     `owner_telegram_id`: у сообщения заполнены `analysis`, `ai_model` и
     счётчики токенов, у задачи — `kind`, `due_at`, `due_precision`;
   - написать «как дела?» — задача не заводится, сообщение с разбором
     остаётся;
   - написать «у меня Toyota Camry» — бот отвечает «Запомнил: Машина —
     Toyota Camry», в `facts` строка `car` со статусом `fact`, задачи нет;
   - Mini App показывает эту задачу в списке, а запись — на вкладке
     «О себе»;
   - надиктовать боту «в пятницу отправить расчёт клиенту» голосовым — он
     отвечает тем же «Записал: отправить расчёт клиенту. Срок: пятница, …»;
     в `messages` строка `kind = voice` с `telegram_file_id`,
     `duration_seconds`, расшифровкой в `text` и `transcript_confidence`;
     в карточке задачи над текстом подпись «Голосовое · 0:0N»;
   - написать «срочно отправить расчёт клиенту» — бот отвечает «Записал:
     отправить расчёт клиенту. К какому сроку?», у задачи заполнены
     `open_question` и `question_asked_at`, `needs_review = true`; следом
     «в пятницу» — «Понял: отправить расчёт клиенту. Срок: пятница, …»,
     у той же задачи появился срок, а `open_question` пуст; второй задачи
     нет;
   - отправить боту фотографию — он отвечает, что понимает текст и голос,
     и ничего не сохраняет.

7. **Проверить правила доступа двумя запросами** — это и есть последнее
   звено связки:

   ```bash
   # только анонимный ключ — ни одной строки (или отказ)
   curl "$SUPABASE_URL/rest/v1/tasks?select=id" -H "apikey: $ANON_KEY"

   # тот же запрос с токеном от telegram-auth — задачи владельца
   curl "$SUPABASE_URL/rest/v1/tasks?select=id" -H "apikey: $ANON_KEY" \
     -H "Authorization: Bearer <токен>"
   ```

   Токен берётся из ответа `telegram-auth` (в Mini App — вкладка Network).

8. **Закрыть строку** «Статус проверки связки» в `techspec/00-adr.md`: что
   проверено, когда, чем кончилось.

Не сошлось — это находка уровня развилки: остановиться и сказать человеку,
а не обходить правила доступа ключом service-role.

## Новая миграция в уже подключённом проекте

Применённая миграция не правится — правка приезжает следующим файлом. Всё,
что не применено, уходит одной командой из корня репозитория:

```bash
supabase db push
```

Так применяется и миграция 003 (`..._understanding.sql`): она добавляет
колонки разбора, заводит `record_message` и `record_understanding` и
**удаляет `record_task`** — бот версии 002 после неё работать перестанет,
поэтому обновляются они вместе. Без CLI — тот же файл целиком в SQL-редакторе
панели проекта.

Так же применяется миграция 004 (`..._reminders.sql`): она заводит таблицу
`reminders` с правилами доступа, функции `due_reminders`,
`mark_reminders_sent`, `mark_task_done` и **пересоздаёт
`record_understanding` с девятым аргументом `reminders`** — бот версии 003
после неё работать перестанет, поэтому обновляются они вместе.

Миграция 005 (`..._complete_task.sql`) заводит `complete_task` — кнопку
«Сделано» в Mini App: владелец берётся из токена, функция выдана только
роли `authenticated`. Бота она не трогает, но без неё Mini App версии 005
не сможет закрыть задачу: применять до публикации приложения.

Миграция 006 (`..._facts.sql`) заводит таблицу `facts` с правилами
доступа и **пересоздаёт `record_understanding` с десятым аргументом
`facts`** — бот версии 005 после неё работать перестанет, поэтому
обновляются они вместе. Mini App версии 006 без неё покажет на вкладке
«О себе» отказ чтения: применять до публикации приложения.

Миграция 007 (`..._voice.sql`) расширяет `messages` под голосовые: виды
`voice` и `video_note`, колонки `telegram_file_id`, `duration_seconds`,
`transcript_confidence`, пустой текст по умолчанию — и **пересоздаёт
`record_message` и `record_understanding` с необязательными аргументами
голоса**. Бот версии 006 с ней работает (новые аргументы необязательные),
а бот версии 007 без неё — нет: применять до перезапуска бота, а в `.env`
к этому моменту нужен `DEEPGRAM_API_KEY`. Mini App версии 007 без неё не
прочитает ни карточку задачи, ни вкладку «О себе» (читает новые колонки
источника): применять до публикации приложения.

Миграция 008 (`..._dialog.sql`) добавляет в `tasks` колонки
`open_question` и `question_asked_at` и **пересоздаёт
`record_understanding` с необязательным тринадцатым аргументом `amend`**
(прежняя версия с двенадцатью удаляется). Теперь функция любой записью,
кроме «не расслышал», снимает открытые вопросы владельца, а с `amend`
дополняет прежнюю активную задачу вместо новой. Бот версии 007 с ней
работает (`amend` необязателен), а бот версии 008 без неё — нет: применять
до перезапуска бота. Mini App новые колонки не читает, публиковать заново
не нужно.

## Проверки

```bash
npm --prefix supabase run typecheck
npm --prefix supabase test
```

Тесты идут на Node: код функций написан на стандартных Web API, поэтому
одинаково работает и в Deno, и в Node, а разработчику не нужен ещё один
рантайм. Подпись в тестах считается независимой реализацией (`node:crypto`),
uuid сверяется с вектором из другой библиотеки — тест ловит ошибку, а не
повторяет её.

SQL не проверяется автоматически: локального стека Supabase (Docker, Deno)
у проекта нет, и миграции с правилами доступа проверяются вживую по
чек-листу выше.
