# supabase — база и Edge Functions

Данные живут в Supabase (Postgres, бесплатный тариф). Своего постоянно
доступного сервера у проекта нет, поэтому Mini App ходит в базу **напрямую**,
а ограничивает её сам Postgres — правила доступа (RLS).

## Что здесь лежит

| Путь | Что это |
| --- | --- |
| `migrations/` | Схема и правила доступа: по файлу на изменение, применяются по порядку имён |
| `functions/telegram-auth/` | Edge Function: проверяет подпись Telegram и выдаёт токен |
| `functions/_shared/` | Общий код функций: проверка initData, подпись JWT, uuid владельца |
| `types/deno.d.ts` | Описание того куска Deno, которым пользуются функции — чтобы `tsc` проверял типы без установленного Deno |
| `config.toml` | Настройки проекта для Supabase CLI |

В базе две таблицы: `messages` — входящие сообщения как есть, `tasks` —
задачи. Обе несут `owner_telegram_id`, на обеих включены правила доступа.
Что в них лежит и почему — `techspec/03-schema.md`, кто и каким ключом ходит —
`techspec/04-access.md`. Применённая миграция не правится: следующая правка —
следующий файл.

## Как проверяется, что человек — это он

1. Telegram открывает Mini App и передаёт ей `initData`, подписанные ключом,
   выведенным из токена бота.
2. Mini App отправляет `initData` в `telegram-auth`.
3. Функция пересчитывает подпись (токен бота знает только она), проверяет
   свежесть `auth_date` и что это владелец, и подписывает JWT секретом проекта.
4. Mini App отдаёт этот JWT в каждый запрос к базе — PostgREST принимает его,
   выдаёт роль `authenticated`, и дальше запрос ограничивают правила доступа.

Без токена запрос идёт с анонимным ключом и роли `authenticated` не получает.

Клеймы токена: `sub` — постоянный uuid владельца (UUIDv5 от Telegram-id),
`telegram_id` — сам id, `role` и `aud` — `authenticated`, срок жизни час.
Правила доступа смотрят на `telegram_id`, а не на `sub`: тот же id знает бот,
и одна колонка служит обеим сторонам без пересчёта uuid
(`techspec/04-access.md` §4.4).

## Первое подключение проекта

Пройден 2026-09-18, связка закрыта (`techspec/00-adr.md`). Список
остаётся на случай нового проекта. Что выяснилось по дороге: секреты
функций не могут начинаться с `SUPABASE_`; на странице JWT Keys ключ
«Legacy HS256» должен оставаться хотя бы в «previously used» — по нему
база проверяет токены функции; загружать функцию без Docker —
`supabase functions deploy telegram-auth --use-api`.

1. **Завести проект** на supabase.com (бесплатный тариф, регион поближе)
   и привязать репозиторий к нему:

   ```bash
   supabase login
   supabase link --project-ref <ref>
   ```

2. **Применить миграции** — из корня репозитория:

   ```bash
   supabase db push
   ```

   Без CLI — открыть SQL-редактор в панели проекта и выполнить файлы из
   `migrations/` по порядку имён, целиком и по одному.

3. **Проверить, что правила доступа включены.** В панели: Database → Tables →
   `messages` и `tasks`, у обеих должен стоять RLS, у каждой одна политика
   `owner only` для роли `authenticated`. Таблица без RLS — находка уровня
   безопасности (инвариант 2), а не недоделка.

4. **Положить секреты функции** (значения — из @BotFather и из Settings → API):

   ```bash
   supabase secrets set TELEGRAM_BOT_TOKEN=... OWNER_TELEGRAM_ID=... \
     JWT_SIGNING_SECRET=...
   supabase functions deploy telegram-auth
   ```

   `JWT_SIGNING_SECRET` — «JWT secret» из настроек проекта (Settings → JWT Keys → Legacy JWT Secret; имя без префикса SUPABASE_ — такие имена Supabase в секретах не принимает).
   Если проект уже переведён на асимметричные ключи подписи и общего секрета
   нет, функция переписывается на выдачу сессии через Supabase Auth — см.
   `techspec/00-adr.md`, строка про проверку человека.

5. **Заполнить `.env`** в корне репозитория по `.env.example`: адрес проекта,
   ключ service-role для бота, адрес и анонимный ключ для Mini App. Проверить
   связь — `uv run --directory bot solomon-health`.

6. **Прогнать путь целиком.** Запустить бота (`uv run --directory bot
   solomon-bot`) и Mini App (`npm --prefix miniapp run dev`, открыть из
   Telegram):

   - написать боту «купить лампочку» — он отвечает «Записал: «купить
     лампочку»»;
   - в таблицах `messages` и `tasks` появилось по строке с вашим
     `owner_telegram_id`;
   - Mini App показывает эту задачу в списке;
   - отправить боту голосовое — он отказывается и ничего не сохраняет.

7. **Проверить правила доступа двумя запросами** — это и есть последнее
   звено связки:

   ```bash
   # только анонимный ключ — ни одной строки (или отказ)
   curl "$SUPABASE_URL/rest/v1/tasks?select=id" -H "apikey: $ANON_KEY"

   # тот же запрос с токеном от telegram-auth — задачи владельца
   curl "$SUPABASE_URL/rest/v1/tasks?select=id" -H "apikey: $ANON_KEY" \
     -H "Authorization: Bearer <токен>"
   ```

   Токен берётся из ответа `telegram-auth` (в Mini App — вкладка Network).

8. **Закрыть строку** «Статус проверки связки» в `techspec/00-adr.md`: что
   проверено, когда, чем кончилось.

Не сошлось — это находка уровня развилки: остановиться и сказать человеку,
а не обходить правила доступа ключом service-role.

## Проверки

```bash
npm --prefix supabase run typecheck
npm --prefix supabase test
```

Тесты идут на Node: код функций написан на стандартных Web API, поэтому
одинаково работает и в Deno, и в Node, а разработчику не нужен ещё один
рантайм. Подпись в тестах считается независимой реализацией (`node:crypto`),
uuid сверяется с вектором из другой библиотеки — тест ловит ошибку, а не
повторяет её.

SQL не проверяется автоматически: локального стека Supabase (Docker, Deno)
у проекта нет, и миграции с правилами доступа проверяются вживую по
чек-листу выше.
