# §0. Закрытые развилки (ADR)

Каждая закрытая развилка — строка: что решали, что решили, почему.
Открытые развилки живут в `spec.md` §«Открытые развилки», сюда переезжают
закрытыми. Решение не переписывается — если оно пересмотрено, добавляется
новая строка со ссылкой на старую.

| Развилка | Решение | Почему | Дата |
| --- | --- | --- | --- |
| Откуда Mini App берёт данные | Напрямую из Supabase под правилами доступа (RLS), без своего API | Постоянно доступного сервера нет и бюджет 0 ₽: размещать API негде. Supabase на бесплатном тарифе отдаёт данные по HTTP, а разграничение делает база, а не прослойка | 2026-09-17 |
| Чем Supabase узнаёт, что запрос от владельца | Edge Function `telegram-auth`: проверяет HMAC-подпись `initData`, сверяет `OWNER_TELEGRAM_ID` и выдаёт HS256 JWT на час; Mini App передаёт его клиенту supabase-js | Подпись `initData` считается по токену бота, а токен в браузер отдавать нельзя (инвариант 1). Edge Functions входят в бесплатный тариф, собственным сервером не являются. Anon-ключ сам по себе владельца не подтверждает — без JWT запрос под RLS не проходит | 2026-09-17 |
| По какому ключу разделяем данные | Колонка `owner_telegram_id` в каждой таблице с данными человека — Telegram-id, а не `sub` токена | Боту известен именно Telegram-id: он же в `OWNER_TELEGRAM_ID` и в клейме `telegram_id`. Одна колонка служит обеим сторонам — и фильтру бота, и правилам доступа, — без пересчёта UUID на каждом запросе. `sub` остаётся в токене для Supabase Auth и на разделение не влияет (§4.4) | 2026-09-17 |

## Статус проверки связки «Mini App → Supabase» (этап 001)

Проверено локально тестами: `initData` с верной подписью принимается,
с подделанной или просроченной — отклоняется; функция выдаёт JWT
с `sub` (UUIDv5 от Telegram-id), `telegram_id`, `role`/`aud` =
`authenticated`, и подпись HS256 сходится независимой проверкой.

**Проверено вживую 2026-09-18** на боевом проекте (миграция 002
применена `supabase db push`, функция задеплоена `--use-api`, без
Docker и Deno):

- `initData`, подписанный токеном бота, → `telegram-auth` выдаёт JWT;
  поддельный — 401;
- `record_task` под `service_role`: задача создана; повторный вызов с
  тем же сообщением вернул ту же задачу, второй не завёл;
- `GET /rest/v1/tasks` с одним anon-ключом → `[]`; тот же запрос с JWT →
  задача владельца; `record_task` под JWT → 403 `permission denied`.

Связка закрыта. Две находки при подключении: проект создан на новых
ключах подписи (ECC текущий, HS256 — «previously used», всё ещё
проверяет токены; **revoke** у него делать нельзя, иначе вход
сломается), и секреты функций не могут начинаться с `SUPABASE_` —
переменная переименована в `JWT_SIGNING_SECRET` (`a52a128`).
