# §4. Доступ к данным

Кто, каким ключом и под какими правилами ходит в базу. Новое правило
доступа пишется сюда, а не в комментарий к коду (`techspec.md`
§«Правила правки»). Решения, откуда взялась схема, — §0.

### 4.1 Три ключа — три роли

| Часть | Ключ | Роль в Postgres | Что ограничивает |
| --- | --- | --- | --- |
| Бот | `SUPABASE_SERVICE_ROLE_KEY` | `service_role` | **ничего** — правила доступа обходятся; фильтр по владельцу пишет код бота (§4.3) |
| Mini App без токена | `VITE_SUPABASE_ANON_KEY` | `anon` | политик для `anon` нет — не видит ни одной строки |
| Mini App с токеном `telegram-auth` | тот же anon-ключ + `Authorization: Bearer <JWT>` | `authenticated` | политики §4.2 по клейму `telegram_id` |

Ключи между частями не пересекаются (§2.1, инвариант 1).

### 4.2 Правила доступа (RLS)

На каждой таблице с `owner_telegram_id`:

```sql
alter table <t> enable row level security;

create policy "<t>: owner only"
  on <t>
  for all
  to authenticated
  using      (owner_telegram_id = (auth.jwt() ->> 'telegram_id')::bigint)
  with check (owner_telegram_id = (auth.jwt() ->> 'telegram_id')::bigint);
```

- Одна политика на все операции: владелец видит и правит только своё,
  чужое для него не существует (не «запрещено», а «нет строк»).
- `with check` не даёт вставить или переписать строку на чужого владельца.
- Для `anon` политик нет намеренно: включённый RLS без политики — отказ.
  Это и есть проверка «без токена — отказ» из `supabase/README.md`.
- Таблица без RLS в `public` — баг уровня безопасности (инвариант 2),
  а не недоделка.
- `owner_settings` (§3.8) — та же политика: ключ таблицы и есть
  `owner_telegram_id`.
- `searches` (§3.10) — та же политика; приложение таблицу не читает,
  поиски пишет и читает только бот функциями `service_role`.
- `chat_sources`, `chat_threads`, `chat_messages`, `chat_analyses`
  (§3.11–3.14, этап 025) — та же политика на каждой; приложение их не
  читает, чужую переписку пишет и читает только бот функциями
  `service_role` (§3.15).
- Правка задачи из приложения идёт только функцией `edit_task` (§3.6,
  `security invoker`, та же политика изнутри). Политика `tasks`
  остаётся `for all`, но прямым `update` приложение задачу не правит:
  перепланирование напоминаний и отметка «срок перенесён» живут в
  функции, и в обход неё они бы разошлись с задачей.

### 4.3 Бот: фильтр по владельцу в коде

`service_role` обходит RLS, поэтому разделение по владельцу для бота
держит код, и держит его в одном месте — `bot/src/solomon/db/`:

- каждая функция `db/` принимает `owner_telegram_id` явно и ставит
  `.eq("owner_telegram_id", owner_telegram_id)` на чтение и правку,
  а на вставку кладёт его в строку;
- слой выше (`services/`) владельца берёт из `Settings`, не из
  сообщения: чужие сообщения до него не доходят (`middlewares.py`);
- запрос к таблице с данными человека **вне `db/`** — нарушение слоёв
  (§2.2), ловится ревью.

### 4.4 Токен

Клеймы и срок жизни JWT — `supabase/README.md`. Правила §4.2 смотрят на
`telegram_id`, а не на `sub`: боту известен Telegram-id, и одна и та же
колонка служит обеим сторонам без пересчёта UUID.
