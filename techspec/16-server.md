# §16. Сервер бота

Где бот живёт постоянно, как устроен на сервере, как туда попадает
новый код и почему процесс бота должен быть один. Mini App и база к
разделу отношения не имеют: статика — на GitHub Pages (§7), данные —
в Supabase.

Решение владельца (2026-10-01): бот переезжает с домашнего компьютера
на сервер VoiceFin. На компьютере бот работает, только пока его
запустили руками, — выключенный компьютер означал день без напоминаний.
Разведка того же дня: опоздавших напоминаний не было (12 из 12 ушли
за 0–1 мин), дыра — в автозапуске, а не в цикле напоминаний (§6.2).

### 16.1 Где живёт бот

| Что | Значение | Почему |
| --- | --- | --- |
| Сервер | VPS автора, на котором работает VoiceFin: Ubuntu 26.04, 2 ядра, 2 ГБ памяти без подкачки | Решение владельца: сервер уже оплачен ради VoiceFin, Соломон к цене не добавляет ничего — бюджет остаётся 0 ₽ (`CLAUDE.md` §«Стек»). Боту нужно около 200 МБ памяти (замер 2026-10-01 на сервере: 195 МБ своей памяти, пик 238 МБ вместе с кэшем файлов) и доля одного ядра |
| Связь | Проверено 2026-10-01: Telegram, Deepgram, Supabase, посредник Claude (§5.1), PyPI, GitHub и сайт uv открываются с сервера. MAX (`platform-api2.max.ru`, 2026-10-07) открывается, но его сертификату сервер не доверяет (`curl` 60): корневой сертификат Минцифры бот носит с собой (§27.2) | Сервер стоит в России; бот VoiceFin ходит оттуда в те же Telegram, Deepgram и Supabase круглые сутки |
| Адрес | В репозитории его нет: скрипты ходят по имени `voicefin-vps` из `~/.ssh/config` на компьютере владельца | Репозиторий публичный (§7.1) — адрес и порт сервера с работающим продуктом в нём не публикуются |
| Вход | `root` по ключу — так заведён сервер; бот работает не от него (§16.2) | Второй пользователь со входом ради выкладки не заводится |

Отвергнуто: сервер другого проекта автора — Telegram оттуда отвечает
с перебоями; отправка напоминаний силами Supabase (`pg_cron` и Edge
Function) — `specs/README.md` §«Чего в очереди нет намеренно».

### 16.2 Как устроено

| Что | Значение | Почему |
| --- | --- | --- |
| Пользователь | Системный `solomon` без входа (`nologin`), домашняя папка `/opt/solomon` | Бот не видит файлов VoiceFin и root, а сбой или взлом бота не выходит за его папку |
| Код | Клон публичного репозитория по HTTPS в `/opt/solomon/secretar-solomon`, ветка `main`; меняется только `git pull --ff-only` | Ключ доступа к GitHub на сервере не нужен. Руками на сервере код не правится — иначе следующий `pull` откажет |
| Python | uv той же версии, что в §1, ставится пользователю `solomon`; Python 3.12 — через uv (`bot/.python-version`); зависимости — `uv sync --frozen --no-dev` по `bot/uv.lock` | Системный Python сервера — 3.14, а бот закреплён на 3.12 (§1); пакеты системы и VoiceFin не трогаются. Проект ставится editable, как `uv sync` делает по умолчанию: `cli.py` ищет `.env` от своего файла |
| Запуск | Служба systemd `solomon-bot` из `deploy/solomon-bot.service`; `ExecStart` — `bot/.venv/bin/solomon-bot`, не `uv run` | Старт не ходит в сеть и не меняет окружение: окружение ставит выкладка (§16.4) |
| Перезапуск | `Restart=always`, `RestartSec=10`; `After=` и `Wants=network-online.target`; `WantedBy=multi-user.target` | Упал — поднимется через 10 с; перезагрузили сервер — стартует сам. Ради этого и переезд |
| Пределы | `MemoryMax=300M`, `CPUQuota=100%` | Подкачки на сервере нет: утечка памяти бота не должна вытеснить VoiceFin — ядро остановит бота, а не чужой процесс. Ядро — одно из двух |
| Защита | `NoNewPrivileges=yes`, `PrivateTmp=yes`, `ProtectSystem=full` | Дёшево и не мешает: на диск бот пишет только файл состояния Instagram в своей домашней папке (ниже), а `ProtectSystem=full` закрывает `/usr`, `/boot` и `/etc`, не `/opt` |
| Журнал | Вывод бота — в journald (`journalctl -u solomon-bot`), `PYTHONUNBUFFERED=1`; своих файлов журнала нет. Значения ключей из каждой строки вырезаются — `<скрыто>` (`cli.py`), и любое `access_token=…` в адресе — тоже | Около 0,7 МБ в день. Журнал общий с VoiceFin, его настройки не меняются. Ключ в журнал попасть может: адрес файла у Telegram несёт токен бота, а aiohttp кладёт адрес в текст своих ошибок — его пишет и aiogram, с трассировкой; адрес продления ключа Instagram несёт ключ, а httpx пишет адрес каждого запроса (инвариант 1) |
| Ключи | `.env` в корне клона: права 600, владелец `solomon`; ровно переменные раздела бота из `.env.example`, `INSTAGRAM_TOKEN`, `ANTHROPIC_BASE_URL`, `MAX_BOT_TOKEN` и `OWNER_MAX_ID` — необязательные (MAX включается только обеими) | Боту больше не нужно. `SUPABASE_ACCESS_TOKEN`, `SUPABASE_DB_PASSWORD`, секреты функций и `VITE_*` на сервер не попадают: на общем сервере лишний ключ — лишний риск (инвариант 1) |

**Бизнес-обновления** (этап 025, `techspec/25-chats.md` §25.2) приходят
тем же long polling: `allowed_updates` aiogram собирает по
зарегистрированным обработчикам, и роутер личных чатов добавляет в опрос
`business_connection`, `business_message`, `edited_business_message` и
`deleted_business_messages`. Входящих соединений и новых переменных
окружения для этого не нужно; включает их владелец — Business Mode в
BotFather и «Автоматизация чатов» в Telegram (`README.md`).

**Файл состояния Instagram** (этап 026, `techspec/26-instagram.md` §26.2) —
`/opt/solomon/state/instagram.json`: действующий (продлённый) ключ
Instagram, его конец, отказ ключа и курсор опроса. Лежит вне клона, чтобы
`git pull` его не видел и в репозиторий он не попал; папку (700) и файл
(600) бот заводит сам от имени `solomon` — `setup-server.sh` их не
создаёт. Ключ в `.env` главнее файла: другой `INSTAGRAM_TOKEN` начинает
файл заново, поэтому новый ключ — это `--env` и перезапуск, а на сервере
ничего не чистится. Нет `INSTAGRAM_TOKEN` — файла нет и не появляется.

**Бот в MAX** (этап 027, `techspec/27-max.md` §27.2) — вторая задача
опроса в том же процессе, рядом с long polling Telegram: свой httpx-клиент
ходит в `platform-api2.max.ru` и ждёт событий до 90 с. Включается двумя
необязательными переменными — `MAX_BOT_TOKEN` и `OWNER_MAX_ID`; нет хотя бы
одной — задачи нет. Корневой сертификат Минцифры лежит в клоне
(`bot/certs/`) и добавляется к проверке TLS только этим клиентом: в систему
сервера ничего не ставится, файлов вне клона бот для MAX не пишет. Отметка
опроса живёт в памяти: после перезапуска MAX отдаёт неподтверждённое снова.
В журнал httpx пишет строку на каждый запрос — без событий около 1000 строк
(~0,15 МБ) в день, токена в них нет: он уходит заголовком. Строку «Run
polling for bot» выкладка ждёт по-прежнему от Telegram; запуск опроса MAX
виден строкой «MAX: опрос запущен».

**Root не работает внутри папки бота.** `git`, `uv` и запись `.env`
идут от имени `solomon` (`runuser -u solomon --`): git под root в чужом
клоне выполнил бы его хуки, а `uv` — сборку пакета, с правами root.
Root только ставит файл службы и управляет ею, а файл службы берёт из
копии репозитория на компьютере владельца, не из клона на сервере:
клоном владеет `solomon`, и через него бот не должен влиять на то, что
root кладёт в systemd.

Первая настройка — `deploy/setup-server.sh`: пользователь, uv, Python,
клон, окружение. Запускается от root (`deploy-bot.mjs --setup`, §16.4),
каждый шаг пропускает, если он уже сделан, и повторный запуск ничего
не ломает. Нет `git` или `curl` — останавливается и называет, чего нет:
пакеты системы — хозяйство VoiceFin. Ключей и адреса сервера в скрипте
нет: адрес репозитория он получает аргументом — `--setup` берёт его из
`origin` владельца в виде HTTPS. Службу скрипт не ставит и бота не
запускает — это делает выкладка.

Файлы `deploy/` уходят на сервер с компьютера на Windows, поэтому в
`.gitattributes` они закреплены с переводом строки LF: systemd и bash
с CRLF не работают.

### 16.3 Один экземпляр

Процесс бота с этим токеном — один, на сервере. Второй long polling
того же бота получает от Telegram 409 (`TelegramConflictError` в
журнале), и обновления делятся между процессами как придётся; а два
цикла напоминаний отправят созревшее дважды — порядок «отправить →
пометить» (§6.2).

Поэтому после переезда на компьютере владельца `solomon-bot` не
запускается — ни руками, ни по привычке в начале сессии. Живая
проверка этапа идёт через бота на сервере, после выкладки. Тесты, в
том числе `pytest -m live`, опрос Telegram не запускают и не мешают;
`solomon-health` только читает базу. Нужна отладка на компьютере —
сначала остановить серверного (`ssh voicefin-vps systemctl stop
solomon-bot`), после — поднять его выкладкой.

Переезд — один раз: первая настройка, остановка бота на компьютере,
выкладка с ключами. Сообщения, присланные между остановкой и стартом,
Telegram хранит до суток и отдаёт новому процессу — бот не сбрасывает
накопленное при старте; созревшие напоминания уходят первым тиком
(§6.2).

Защиты от второго экземпляра в коде нет: правило держится
документами, а нарушение видно в журнале по 409.

### 16.4 Выкладка

Новый код попадает на сервер после push в `main` (§7.2, `CLAUDE.md`
§«Сдача изменения»), по шагам:

1. Миграции этапа, если есть, — в базу до выкладки: новый код может
   звать новые функции базы.
2. Push в `main` с чистыми воротами — он же публикует Mini App (§7).
3. `node scripts/deploy-bot.mjs` с компьютера владельца.

Скрипт выкладки:

- до первого обращения к серверу отказывает, если рабочее дерево не
  чистое или `HEAD` не совпадает с `origin/main`: сервер берёт код с
  GitHub, и незапушенное туда не попадёт;
- на сервере от имени `solomon` — `git pull --ff-only` и `uv sync
  --frozen --no-dev`; файл службы отличается от
  `deploy/solomon-bot.service` владельца или его нет — root ставит
  новый и перечитывает systemd; автозапуск включается каждой выкладкой;
  затем `systemctl restart solomon-bot`. Шаг на сервере не удался —
  бот не перезапускается;
- проверяет: служба `active`, в её журнале с момента перезапуска — строка
  aiogram о начале опроса (`Run polling for bot`), ждёт до 60 с; коммит
  на сервере равен `HEAD`. Иначе — отказ и последние строки журнала,
  строки вида токена бота и `access_token=…` в нём скрыты. `TelegramConflictError` после
  перезапуска — предупреждение о втором экземпляре (§16.3), не отказ;
- ходит `ssh voicefin-vps` без вопросов (`BatchMode=yes`) и с таймаутом
  соединения: зависнуть на запросе пароля он не может.

Флаги:

| Флаг | Что делает |
| --- | --- |
| `--env` | Выкладка, и перед перезапуском — ключи. Список переменных читается из раздела бота в `.env.example`, а не дублируется в скрипте; значения берутся из `.env` владельца, уходят на сервер через stdin `ssh` — не в аргументах команды — и не печатаются, в выводе только имена. Переменной в `.env` нет — она не копируется: обязательные проверит сам бот при старте (`config.py`), и проверка выкладки увидит отказ. Нет `.env` или в нём ни одной переменной из списка — отказ до обращения к серверу: пустой файл стёр бы ключи на сервере. Строки уходят с LF |
| `--status` | Ничего не меняет: состояние службы и автозапуска, коммит на сервере против `HEAD`, память службы, время старта, последние строки журнала |
| `--setup` | Первая настройка: `deploy/setup-server.sh` из копии владельца уходит на сервер через stdin `ssh` и выполняется от root (§16.2) |

Выкладывает оркестратор — после закрытия этапа, менявшего `bot/`, — или
владелец своей командой. Исполнитель этапа push и выкладку не делает
(`CLAUDE.md` §«Сдача изменения»).

Отката у скрипта нет: выкладка, которая не поднялась, исправляется
новым коммитом — правкой или `git revert`, — push и выкладкой. На
сервере руками код не правится (§16.2).

### 16.5 Сбои

| Что случилось | Что происходит | Где видно |
| --- | --- | --- |
| Бот упал | systemd поднимает его через 10 с, без предела попыток | `--status`: время старта; журнал |
| Сервер перезагрузили | Служба стартует сама; созревшее за простой уходит первым тиком (§6.2) | `systemctl is-enabled solomon-bot` — `enabled` |
| Сервер недоступен | Напоминания ждут в базе и приходят после подъёма — как раньше при выключенном компьютере | Снаружи — никак: мониторинга нет (§16.6) |
| Бот съел больше 300 МБ | Ядро останавливает бота, systemd поднимает; VoiceFin не задет | Журнал: `oom-kill` |
| Новый код не стартует | Скрипт выкладки отказывает с хвостом журнала, systemd перезапускает бота раз в 10 с, пока не придёт исправление (§16.4) | Вывод выкладки, `--status` |
| Запущен второй экземпляр | 409 в журналах обоих, напоминания могут прийти дважды (§16.3) | Журнал: `TelegramConflictError` |
| Один IP базы не отвечает | У адреса базы два IP, и с сервера один временами молчит. Соединение ждёт его 5 с и берёт второй; молчат оба — ещё одна попытка. Чтение и запись ждут по-прежнему до 120 с (`db/client.py`). Раньше клиент ждал соединения 120 с, и тик опаздывал на две минуты — вечерами почти через раз, с 2026-10-02 | Журнал: тики через 3 мин вместо минуты — значит, ожидание соединения снова длинное |
| MAX не отвечает | Опрос MAX ждёт 5 с, дальше вдвое до минуты и спрашивает ту же отметку — пропущенное приходит, когда MAX ответит; опрос Telegram и напоминания не задеты (§27.2) | Журнал: «Опрос MAX не удался»; отвергнутый токен — «Ключ MAX_BOT_TOKEN не подошёл» |
| Связь с Telegram зависает | С сервера соединение с Telegram временами не устанавливается. Раньше запрос висел весь срок — минуту: ответ в чате опаздывал или терялся, повисший «печатает…» держал ответ (2026-10-03, 2026-10-05). Теперь соединение ждут 5 с и пробуют заново, пока не выйдет прежний срок запроса; запрос, который уже ушёл, не повторяется — дублей нет. «печатает…» ответ ждёт не дольше секунды (`telegram.py`) | Журнал: «соединение не установилось», следом «соединение с попытки N» — связь вернулась; `no connection in N attempts` — не вернулась за срок |

### 16.6 Что не делает

- Не трогает VoiceFin: его контейнеры Docker, Caddy, папки, брандмауэр,
  подкачку, настройки журнала, обновления системы и перезагрузку —
  даже когда сервер просит перезагрузки после обновлений: это решение
  VoiceFin. Автозапуск проверяется `systemctl is-enabled` и остановкой
  процесса, а не перезагрузкой сервера.
- Не открывает портов и не заводит API: long polling Telegram и опрос
  MAX ходят наружу сами (вебхук MAX потребовал бы входящий адрес), а Mini
  App по-прежнему работает с базой напрямую (§0).
- Не собирает образ Docker: systemd и uv хватает, а Docker сервера —
  хозяйство VoiceFin.
- Не выкладывает из GitHub Actions: ключ входа на сервер VoiceFin в
  секретах GitHub дал бы тому, кто доберётся до репозитория, вход на
  сервер с работающим продуктом.
- Не следит за ботом снаружи: оповещений о падении нет; сбой видно по
  пропавшим напоминаниям и `--status`.
- Не защищается от второго экземпляра кодом (§16.3) и не откатывает
  выкладку сам (§16.4).
- Не хранит на сервере ничего, кроме кода, окружения, `.env` и файла
  состояния Instagram (§16.2): данные — в Supabase.
- Не фильтрует workflow Pages по путям: push с правкой одного бота
  пересобирает ту же Mini App — лишняя минута Actions, не ошибка.
